## 1. What the issue asks, and its binding design decisions

Goal (quoted): *"The frame-time tail of the real, presenting game window at the
display's resolution, from process start, is measured on each dev machine, and
each listed stutter suspect is confirmed or refuted with a number."*

Binding decisions (quoted, abbreviated only where marked `…`):

1. *"**`--bench walk --window`.** Runs the real presenting surface (the game's own
   window, `winit`, `chosen_present_mode`) at the display's resolution, with the
   scripted walk of #323, for **60 s from process start** — so startup is
   included: the `--bench tune` child, settings load, first-use pipeline compiles.
   It prints `PRESENT: p99 / p99.9 / max ms, over 16.7 ms N, over 33.3 ms M (F
   frames)` where a sample is **present-to-present** (the wall-clock gap between
   consecutive returns of `surface.present()` on the app's thread; `Instant` is
   allowed in `cubara` and `cubara-render`). Rule 5: the windowed bench drives the
   same `Game` and `encode_scene` as play, with the walk script as input; no
   second game loop. The summary line also prints the window size and present
   mode actually obtained."*
2. *"**One row per suspect** … (a) tune child on vs off (a `--no-tune` switch if
   one does not exist, passed through to `Game`; the "on" run is the default
   start); (b) `PresentMode::Mailbox` vs `Fifo` (a `--present mailbox|fifo`
   switch; the renderer already returns the concrete mode it got, so the line can
   say which one ran); (c) a pipeline rebuild mid-walk: whatever today triggers
   `build_pipeline` at runtime (a settings change such as far quality; the
   implementer names it) is fired at t = 30 s and the frame it lands on is
   reported separately. Each row records the max frame and how many frames
   exceeded 33.3 ms, with the thermal protocol and run count."*
3. *"**Which surface item 0 measures is written down, not changed.** … This issue
   adds one clarifying line under `ROADMAP.md`'s item 0 saying which surface the
   frame terms are measured on (offscreen 1920×1080 today) and the owner approves
   that line in the PR. Whatever he decides, the windowed trace is a **recorded
   companion row** per machine in `BENCHMARKS.md` …"*
4. *"**A confirmed suspect is fixed in its own issue** … This issue builds the
   instrument and reports; it does not fix."*
5. *"**The sampling is a pure function with unit tests** (p99/p99.9/max/over-threshold
   counts over a slice of gaps), separate from the window code …"*

Done-when items that shape the work: tests seen to fail — *"(a) the statistics

## 3. Approach, and why

**One instrument, inside the real window loop.** `--bench walk --window` starts the
normal `App` (`main.rs`) — same `resumed`, same `RedrawRequested` body, same
`Renderer::render` → `encode_scene` — with one extra `Option<WindowBench>` field.
When it is `Some`, three things happen in `RedrawRequested`: the walk script
presses keys on `Game` before `advance`; the instant `queue.present` returned is
recorded after `render`; and at 60 s from process start the line is printed and
the loop exits. No second loop, no second render path (Rule 5; decision 1).

**The renderer reports the present instant itself.** `Renderer::render` returns
`Option<Instant>`: `Some(t)` taken on the line after `self.queue.present(frame)`,
`None` when it drew offscreen or skipped the frame (F5). Timing in `main.rs`
after `render()` returns would silently count skipped frames as presents.

**Statistics are `WorkTail::of`, plus a small pure module** (`present.rs`) that
turns present times into gaps, splits startup from steady state, lists the worst
gaps with their timestamps, and formats the line. Tested with no display
(decision 5).

**What counts as a stutter** (present-to-present gap, app thread, 60 Hz panel):

| Term | Threshold | Status |
|---|---|---|
| `over 16.7 ms` | > 1/60 s | the issue's and item 0's interval — printed because the issue's line format requires it. **Under Fifo it is meaningless**: every frame sits at 16.67 ms ± wake-up jitter, so about half of them land over. Do not use it to compare Fifo with Immediate. |
| `over 25.0 ms` | > 1.5 × 1/60 s | **chosen, not derived.** A gap this long means a refresh went by with no new frame. Same factor as `FrameWatch`'s `MISSED = 1.5` (`options.rs:96`), so the instrument and the game's own step-down rule agree on what a missed frame is. This is the term to compare Fifo with Immediate on. |
| `over 33.3 ms` | > 2 × 1/60 s | from gate item 0 ("no frame exceeds 2× the refresh interval at 60 Hz") and the issue. **The verdict term.** |
| steady state begins | 10 s after process start | **chosen, not derived** — equal to `SETTLE_SECONDS` (`options.rs:90`), the game's own "loading is over" allowance. The line reports the whole 60 s (the issue's requirement) *and* the part after 10 s, so loading hitches and play hitches are not one number. |
| worst gaps listed | 5 | **chosen, not derived.** With timestamps, so a hitch can be matched to an event (tune child ending, the rebuild at 30 s). |
| rebuild attribution window | largest gap in the 1.0 s after the resize is requested | **chosen, not derived.** |

**Suspect (c) is a window resize.** Named per decision 2 ("the implementer names
it"), from F8: the only synchronous runtime pipeline build is `SceneRenderer::resize`.
At `--rebuild-at 30` the bench asks the window for an inner size 2 px shorter
(`request_inner_size`), which goes through the game's own `Resized` handler.
Windowed runs only (a fullscreen window cannot be resized; the flag is refused
with `--fullscreen`). `Renderer::resize` also logs how long `scene.resize` took,
so the pipeline build is separable from the surface reconfigure in the same gap.

**What a present-to-present gap shows, per mode** — this goes in the footnote, in
the PR body and in the report to the owner, in these words or close to them:

| Mode on the M3 | What the app-thread gap is | What it shows | What it cannot show |
|---|---|---|---|
| **Fifo** (`displaySync` on, `metal/surface.rs:261-264`; 3 drawables, `nextDrawable` blocks with no timeout, `:330-333`) | Gated by the display: the loop cannot get a drawable until the compositor has released one, so gaps sit at the refresh interval. | **The closest this instrument gets to the glass.** A gap of two intervals is a refresh that showed the previous frame. `over 25.0 ms` and `over 33.3 ms` are missed refreshes. | Whether a frame handed over on time was shown on time; a frame the compositor dropped by itself. |
| **Immediate** (the M3's default — Metal offers no Mailbox, F6) | The loop's own cadence, about 1 ms at 1,000 FPS. Most frames are never shown at all. | **Only that the app thread did not hitch.** A gap over 16.7 ms still proves a refresh showed a stale frame. | Which frames reached a refresh, and whether what reached it was evenly spaced. A clean Immediate row says the loop is smooth, not that the picture is. |

wgpu 30 has no presented-time API (no `presented`/`presentedTime` anywhere in
`wgpu-hal-30.0.1/src/metal/`; present is `presentDrawable` + commit,
`metal/mod.rs:802-820`), so on-glass time is out of reach without `as_hal` and
`unsafe`. **If both the Fifo and the Immediate rows come out clean and the owner
still sees stutter, the next step is named, not guessed at: a follow-up issue,
"3.0a: on-glass frame times on Metal", that reads `MTLDrawable.presentedTime`
(via `addPresentedHandler`, through wgpu's `as_hal`) for the same 60 s walk and
reports the same terms on those timestamps.** Draft that issue's text in the
report; do not build it here (decision 4).

**The wait inside acquire is recorded separately.** Under Fifo a stutter the
player sees is most likely a long block in `get_current_texture`; `render()`
therefore also reports how long that call took (A1.4), and the line gives its
p99.9 and max, so "the loop was slow" and "the display made it wait" are two
numbers.

### Alternatives rejected

- **Timing in a new loop in `flight.rs` that opens its own window.** A second game
  loop; decision 1 and Rule 5 forbid it, and it would not include `resumed`'s
  startup work.
- **A second percentile function for presents.** `WorkTail::of` already answers
  the question (F3).
- **On-glass timestamps via `MTLDrawable.addPresentedHandler` / `as_hal`.** Unsafe,
  Metal-only, and outside what the issue binds. If the app-thread trace is clean
  and the owner still sees stutter, that is the follow-up issue to propose — not
  something to add here.
- **macOS Metal Performance HUD (`MTL_HUD_ENABLED=1`) as the measurement.** It
  draws into the frame it measures and its numbers are read by eye. Not used for
  any row. It may be mentioned to the owner as something he can turn on himself.
- **Firing a far-quality change as suspect (c).** It rebuilds no pipeline (F8). A
  far reset is real and is already exercised by the tune-on run; `far` in the line
  shows it.
- **`renderer.resize(w, h-2)` called directly, without resizing the window.** On
  Vulkan a swapchain extent that differs from the window's is rejected, and the
  issue's rows are for Linux and Windows too.
- **Refactoring `walk()` wholesale to share a loop with the window.** Out of scope
  ("The offscreen benches' behaviour"). Only the key script is shared.
- **Running in the owner's world to reproduce "his" stutter.** `CLAUDE.md` forbids
  touching `saves/`.

/// The keys `--bench walk` presses, for whichever loop runs it: W held, Space
/// once a second -- or, with `fly`, F4 on the first frame and then W.
pub struct WalkScript { fly: bool, phase: Phase, next_jump: f32, jumping: bool }

impl WalkScript {
    pub fn new(fly: bool) -> Self            // phase Start, next_jump 1.0
    /// Before a frame's `Game::advance`; `t` is seconds since the script began.
    pub fn before(&mut self, game: &mut Game, t: f32)
    /// After that frame.
    pub fn after(&mut self, game: &mut Game)
}
```

- `before`: `Start` + fly → `key_input(F4, true)`, phase `ReleaseF4`, return.
  `Start` + walk → `key_input(KeyW, true)`, phase `Moving` (fall through to the
  jump check). `Moving`: if `!fly && t >= next_jump` → `key_input(Space, true)`,
  `next_jump += 1.0`, `jumping = true`.
- `after`: `ReleaseF4` → `key_input(F4, false)`, `key_input(KeyW, true)`, phase
  `Moving`. If `jumping` → `key_input(Space, false)`, `jumping = false`.

```

The whole-run numbers come from `WorkTail::of` over every gap's `took`

  and the last run of every session**, in addition to A-off's own three runs in
  the rotation. Immediate is uncapped, so its frame count is the session's load
  gauge: a machine that is busy presents fewer frames in 60 s.
- **Drift:** if the last control's frame count differs from the first's by more
  than **7% (chosen, not derived — set under the 11–14% that ⁸⁹'s agents cost, so
  that kind of load cannot hide inside it)**, the session drifted: every row of
  it is recorded with that stated in the footnote, no verdict is drawn from it,
  and the session is repeated once at another quiet time. Both sessions stay in
  the file.
- **Per run:** `Frames` is a column. A run under Immediate whose frame count is
  more than **7% (chosen, not derived)** from the median of its own configuration
  is flagged in the footnote and the configuration gets one more run. Under Fifo
  the count is pinned near 60 × seconds by the display and says nothing about
  load — there, a count more than **1% (chosen, not derived)** *below* 60 × the
  seconds presented means missed refreshes, which is the result, not a flag; the
  load evidence for Fifo runs is the controls on either side.
- **If the measurement is split over more than one session** (or repeated after
  a code change), each session opens and closes with the control, and the
  footnote compares controls **between** sessions with the same 7% margin before
  comparing anything else across them.
- If the A-off control shows about 60 × seconds frames (Immediate is being paced

### Verdict rule (the issue's, made exact; the exact form is chosen, not derived)

## 8. Risks, and what I am unsure of

- **Biggest: the instrument may be clean while the owner still sees stutter.** It
  measures the app thread; Metal presents asynchronously (F6). Immediate — his
  default mode — shows app-thread hitches only; Fifo is the closest to the glass
  (section 3's table). The plan says so wherever a number is reported, and names
  the on-glass follow-up rather than building it.
- **The acquire clock adds two `Instant::now()` calls to every window frame** (not
  to offscreen frames). Tens of nanoseconds against a ~1 ms frame; the `--bench
  gate` pair in PR B does not exercise the window path, so this cost is argued,
  not measured.
- **The idle-time check is a proxy** for "he is not using the machine": it cannot
  see him reading the screen. His word overrides it; the announcement to the
  contact session is what gives him the chance to say it.
- **Is Immediate really uncapped in a window on this Mac?** The comment at
  `render.rs:728-737` recalls the window sitting at exactly 60 FPS under the old
  `AutoNoVsync`. If A-off shows about 3,600 frames in 60 s, macOS is pacing the
  window regardless of mode — a finding to report first, because then (b) has no
  "off" on this machine.
- **Fullscreen size and the notch** (F13) — unverified; winit's borderless
  fullscreen on macOS is native fullscreen (`toggleFullScreen:`), which animates
  for most of a second at startup. That transition is inside "from process
  start" and will appear in the first seconds' gaps; the after-10 s numbers are
  the ones to read for play.
- **`request_inner_size` on macOS** may apply immediately or deliver `Resized`
  later; step A4.8c handles both, but I have not seen which happens. If the
  window refuses, the line says so and row (c) is reported as not obtained — do
  not fake it with a direct `renderer.resize`.
- **Does the window take focus when launched from a background script inside the
  Claude app?** winit activates the app by default; unverified here. `focus lost`
  and `skipped` in the line are the check.
- **The tune child may not finish inside 60 s** while sharing the GPU; then the
  "on" row never includes the far reset. Reported as such.
- **The executing session is itself background load.** One waiting session is the
  minimum possible; ⁸⁹ measured four streaming agents, not one idle one. Unknown
  how much one idle session costs — say so in the footnote. The controls detect
  load that *changes* during a session; a load that is constant from first
  control to last is invisible to them, which is why the hard no-agent rule is
  a rule and not a measurement.
- **The walk barely moves** (26 blocks in 30 s before it stops against terrain,
  ⁸³), so the walk rows measure tick + present, not streaming. The fly rows are
  there for that; the issue's six suspect rows are still the walk, as it binds.
- **`WalkScript` changes `walk()`'s code though not, by reading, its key

  a regression in the refactor, not noise — compare one offscreen walk before and

- **Line numbers will have drifted**; `origin/main` was already ahead of the tree
